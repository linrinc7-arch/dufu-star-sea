## 0-B. 一句话判断

这是一份**手写得非常干净**的 Canvas 2D 作品：零依赖、零外部请求、单帧 11–13 ms、无内存泄漏、离线可跑。它的问题不在「写得糙」，而在**主流程没有分段保护**——我注入 6 种现实故障，评审初期 **2 种让页面永久停在「PICKING STARS」且一个字提示都没有**、**3 种让整块内容静默消失**；作者中途补了全局兜底，把前 2 种降级成「有字的错误页」，但后 3 种原样未动，而且整页不可用的本质没变。对一件要在别人电脑上双击打开的作品，这仍是最贵的一类缺陷。

## 3. 实测数据

### 3.1 首屏（含 6× CPU 降频）

| 指标 | 1× 热机（n=6，中位 / 区间） | 1× 冷机（n=2，首次冷启动） | 6×（n=2） |
|---|---|---|---|
| First Paint | 250 / 132–1,048 ms | 156 ms | 476–560 ms |
| First Contentful Paint | 250 / 132–1,048 ms | 156 ms | 476–560 ms |
| DOMContentLoaded | 540 / 383–1,002 ms | **2,297 / 2,383 ms** | **2,296–2,751 ms** |
| `load` 事件 | 同 DCL | 同上 | 2,755 ms |
| 开场遮罩移除（可看见星海） | **2,050 / 2,008–2,636 ms** | **3,097 / 3,195 ms** | **4,169–4,521 ms** |
| 最长单次主线程阻塞 | 291 / 215–895 ms | **1,872 / 1,878 ms** | 1,551–1,656 ms |

**第一列和第二列是同一份代码、同一台机器。** 现象上的差别是「这是不是隔了一段时间之后的第一次打开」——首帧的首次全屏合成在冷态下会一次性吃掉 ~1.8 秒（机制见 §3.6，未逐项证实成因）。也就是说：**答辩现场第一次双击打开，看到的更可能是右边那一列。**

**关键结论：首屏那 2 秒里，真正干活的时间只有 ~0.5 秒（热机口径）。**

- 解析三个数据脚本：DUFU 987 KB → 61 ms；ART_DATA 4.74 MB base64 → 61 ms；SHIYUN → 1 ms；合计 **123 ms**（打点 `afterSHIYUN=123`）。
- 启动链（`makeGrain … buildBloom`）合计 **246 ms**（6× 下 1,741 ms）。
- 剩下的 ~1.4 s 是**刻意的开场动画**：`_bootMin=900` + 数字从 0000 滚到 1468（34 拍 × 40 ms = 1,360 ms）+ 700 ms 退场。这是设计选择，不是性能问题——但答辩时若说“首屏 2 秒”，要有能力拆开讲。

开机分步耗时（自注入计时，1× → 6×）：

| 步骤 | 1× (ms) | 6× (ms) | 占比(1×) |
|---|---|---|---|
| `makeGrain` | 31.1 | 37.6 | 12.6% |
| `buildNebulaTex` | **166.1** | **1,224.5** | **67.5%** |
| `buildPoemModel` | 29.9 | 315.3 | 12.2% |
| `buildCone`（9000 粒） | 2.1 | 17.4 | 0.9% |
| `buildSky` ×2 | 2.2 | 8.7 | 0.9% |
| `render(0)` | 12.3 | 123.2 | 5.0% |
| 其余（WC/layout/bloom/resize） | 2.3 | 14.4 | 0.9% |
| **合计** | **246** | **1,741** | |

> 顺带纠正一处事实：天幕纹理的**计算分辨率是 512×256**（`NEB={TW:2048,TH:1024,W:512,H:256}`，行 1113），不是 1024×512；算完再 4× 上采样到 2048×1024。这解释了为什么它只花 166 ms——131,072 像素 × 21 次 `nVal`，约 2,200 万次 hash。

### 3.2 帧率与单帧成本

| 场景 | 结果 |
|---|---|
| `render()` 单帧同步耗时（DPR 1） | **11.5 ms** 均值 / 13.5–14.3 ms p95 |
| DPR 1.5（2160×1350 画布） | 11.4 ms —— **不变** |
| DPR 2（2880×1800 画布） | 12.0 ms —— **不变** |
| 6× CPU 降频 | **79.5–82.0 ms** 均值 / 97–105 ms p95（≈ 12 fps，两次独立测量） |
| 交互选诗 → 诗卡可读 | **24 ms**（1×）/ **258 ms**（6×） |
| rAF 帧间隔（忙态） | p50 6 ms / p95 11.9 ms / max 62–144 ms |
| 空闲 | 代码主动降到 20 fps（`busy?16.7:50`，行 1803） |

**有两点值得写进答辩**：

1. **DPR 无关**是本作一个被低估的优点：画布像素从 1440×900 涨到 2880×1800，单帧成本纹丝不动。说明瓶颈在**每帧约 1 万次 `drawImage` 的调用开销**（CPU 提交），不在填充率（GPU）。所以它在高分屏上不会突然变卡。
2. 反过来说，**它吃的是调用次数**：6× 降频下单帧 82 ms，与“调用开销线性放大”完全吻合。低端本（比我这台慢 2–3 倍）就是 25–35 ms/帧，即 28–40 fps——而作品默认 60 fps 目标，掉帧会直接可见。

层级别 A/B（关掉某一层再测单帧，n=1，同机连续跑）：

| 变体（同源自打点副本 v7，基准 10.8 ms） | 单帧 ms |
|---|---|
| 对照 v7（含打点开销） | 10.8 |
| 关泛光 `applyBloom` | 11.8 |
| 关诗云 9000 点 `drawPoemCloud` | 10.7 |
| 关天幕 `drawNebula` | 12.9 |
| 三层全关 | 11.2 |

（未打点的原版为 12.6 ms；把它和上表混着比是没意义的，所以上表只用同一份副本横比。）

差异全在噪声内——**没有单一热点**，成本摊在 1,468 颗诗星 + 全屏暗角 + 全屏合成的总和上。真要做性能优化，方向是“减少每帧调用次数”，不是“优化某个函数”。实时采样剖析也印证：忙态 3 秒窗口内 `drawImage` 占 19.3% 的采样，`render` 自身只占 1.4%。

**这是本次评审最刺眼的一张表**：号称“天幕由代码生成、不用任何图片”的作品，其单文件的 **79% 是图片**。程序化天幕只占 115 KB（1.9%）。不是说要删图，而是**“6 MB 单文件”这个卖点其实是“4.7 MB 相册 + 1.3 MB 作品”**。

三个可直接回收的浪费：

1. **孤儿图**：`ART_DATA` 有 31 个键，`DUFU.art` 只有 30 个 slug，键 `20261020-000049-gpt-0`（149,668 B base64 ≈ **112 KB**）**永远不会被查到**——`window.ART_DATA[slug]` 只会用 slug 查。占全文件 1.9%，纯死重。

3. **`sky.jpg`（398 KB）** 在 `杜诗星海_全图版/` 里躺着，`index.html` 中对 `sky.jpg` 的引用数 = **0**。

### 3.5 离线可用性

✅ **完全离线可用**，证据：

- 单文件里 `fetch(` / `XMLHttpRequest` / `new WebSocket` / `import(` 出现次数 = **0**
- `@import` = 0，`fonts.googleapis` = 0，`cdn.` = 0
- 冷启动网络日志只有 **2 条**：文档本身 + `art/all/0824.jpg`（我在仓库根目录打开时该图不存在，故 404）

### 3.6 双峰分布：首帧的 1.8 秒尾延迟（这是本次最该修的性能问题）

全部 10 次冷启动里，有 **2 次**出现同一种形态：解析和启动链都在 0.4 s 内完成，然后**单个任务卡住 ~1.87 秒**，DCL 被推到 2.3 s，遮罩到 3.1 s 才抬起来。

用 §8 的 `v7_stamps.html` 打点抓到的那一次是这样的：

| 打点 | 时刻 |
|---|---|
| 数据脚本解析完 | 61 ms |
| ART_DATA 解析完 | 122 ms |
| IIFE 开始 | 126 ms |
| **启动链跑完（含 render(0)）** | **392 ms** |
| **首个 rAF 帧完成** | **2,226 ms** ← 1,834 ms 全挂在这一帧 |

也就是说：**不是启动算法慢，是“第一次真正把这一帧合成出去”慢。**

- 其余 8 次同配置为 383–1,002 ms，说明这不是常态；
- 但两次都发生在“一段时间以来第一次打开”，也就是**最接近真实观众第一次双击的那种状态**；
- 代码里**没有任何“首帧兜底”**：遮罩是在“两个 rAF 之后”关掉的，不是“首帧真的提交之后”关掉的。如果首帧要 1.8 s，用户会先看到 2 秒静止的黑屏，然后画面才出来——中间没有任何反馈。

最可能的成因（未逐项证实，但方向明确）：2048×1024 贴图首次上传 + 全屏 `lighter` 混合 + `ctx.filter='blur(7px)'` 首次编译模糊着色器 + 全屏 `mix-blend-mode:overlay` 颗粒层，四件事挤在同一帧里做。**在核显机器上，这四件事只会更慢。**

处理建议见 §6 性能行 ③：把遮罩的抬起条件从“两个 rAF”改成“首帧真的提交”，并在首帧之前先画一帧纯渐变（成本近乎 0），让用户先看到东西。

| 6 | `getImageData` 抛错（模拟显存/跨域/内存受限） | 前两版：**永久停在「PICKING STARS」**；10:40 版：走同一条错误通道显示统一错误页（v3 已实测文本确认，本项未逐字复测） | `buildNebulaTex` 抛错 | ⚠️ 同上：有话说，但用不了 |

**修订前的口径是「2 种全黑，3 种静默，1 种有兜底」。** 评审末期作者补了一个全局兜底（脚本 #9，1,672 B），把「全黑」降级成「有话说但用不了」；「静默」那三条（#2、#4、#5）原样未动。这张表仍是本次评审最值钱的部分——**因为它描述的是同一类结构性风险，而兜底只解决了其中一半**。

### 4.2 代码定位（行号基于 §1 所述的快照 `评审/_r10/snapshot_build.html`，sha1 `d076974a`；文件此后仍被改动过，按函数名定位更稳）

**① 启动链是一条没有任何保护的直线**（行 3341）：

```js
makeGrain(); buildWC(); buildSky(); buildMW(); buildSky(); SKY=null;
buildNebulaTex(); layoutGalaxyPoems(); buildPoemModel(); buildCone(); buildBloom();
```

这条线**下面 20 行**才有 `resize(); render(0); requestAnimationFrame(loop);` 和兜底：

```js
requestAnimationFrame(function(){ requestAnimationFrame(bootReady); });
setTimeout(bootReady, 6000);   // 兜底：任何情况下 6 秒都要进去   ← 行 3374
```

**问题就在这**：兜底自己排在被保护对象**后面**。上面任何一步抛错，这个 IIFE 立刻中止，`setTimeout(bootReady, 6000)` **根本不会被注册**——「任何情况下 6 秒都要进去」的注释是一句做不到的承诺。前两版实测 #3、#6 正是死在这里。

**10:40 版补了一层 window 级兜底之后，user 能看到话了，但结构没变**：`makeGrain()` 抛错 → 后面 10 个构建函数全不执行 → `resize/render/loop` 全不执行 → 即使错误页写着「可以试试刷新一次」，刷新还是同样的结果。**兜底解决的是「知情权」，不解决「可用性」。**

**② 守卫只检查“存在”，不检查“可用”**（行 667）：

```js
if(!window.DUFU){document.body.innerHTML='<div …>数据未加载，请使用发布版单文件。</div>';}
```

它只问 `window.DUFU` 在不在。数据脚本整体语法错时有效（#1），**但 schema 漂移时完全无效**（#3：`DUFU` 在，`cats` 不在）——而 schema 漂移恰恰是数据管线跑完忘了同步字段时最常见的形态。

**③ 全局兜底：评审末期有了，但只覆盖一条通道**（脚本 #9，行 722 起）

它做了三件对的事：`error`（capture）+`unhandledrejection` + 8 秒 watchdog，并且**排在应用脚本之前**——这正好是我要给的第 1 条建议的前半段。

但它漏掉三类，且都不是边角：

- **同步调用栈内被吞的异常**：0-A 那条 `_col` 就是——`select()` 抛在 click 处理里，事件没冒到 `window`，兜底不会触发，页面表现是「点了没反应」，连错误页都没有。
- **静默降级**：`ANALYSIS`/`COLLATION` 缺失时，代码走 `||{}`，不抛错，兜底永远不知道少了东西。
- **卡住而不是抛错**：如果某一步是死循环或长阻塞，`error` 不会来；8 秒 watchdog 只能报「加载超时」，报不出是哪一块。

另外它有个小坑：`showFatal()` 是直接改 `#load` 的 `innerHTML`，**没有先移除 `.up` 这个类**。如果错误发生在 `bootReady()` 加上 `.up` 之后、`#load` 被移除之前的那 700 ms 窗口里，错误页会写进一个已经淡出/位移的容器，用户看不见。

**④ 可选数据模块一律 `||{}` 静默降级**（`ANALYSIS` 行 2285、`COLLATION` 行 2888、`SHIYUN` 行 1824）：

```js
var an = (window.ANALYSIS||{})[p.t];     // 拿不到就当没有
var _col = (window.COLLATION||{})[p.t];  // 拿不到就当没有
if (syBuilt || !window.SHIYUN) return;   // 拿不到就不建
```

从“不崩”的角度这是**正确的写法**，比大多数学生作品强。但它把“这一块坏了”和“这一首诗本来就没有”变成**同一个视觉结果**。交付前没人会发现，交出去之后也没人会告诉你。

**⑤ 四个空 `catch` 全部良性**（`ctx.filter` 一处、音频三处、`localStorage` 一处）——这几处不用改。

### 4.3 结论

- **异常处理覆盖度：边角 100%，主流程从 0% 补到「有一层网」。** 所有 `try/catch` 仍花在 filter / localStorage 这类可有可无的地方；主流程现在有了一张 window 级的网，但**没有分段保护、没有数据形状校验**，掉进网里就是「整页不可用 + 一句道歉」。
- **静默失败不是偶发，是结构性的**：`||{}` 降级 + 无 schema 校验 + 兜底只看 uncaught，三者叠加，使得「整块功能消失」仍是默认结局。0-A 的 `_col` 就是最新例证：一行没声明，整个「点星读诗」全死，而页面安静得像什么都没发生。

## 5. 三条最伤 + 可执行改法

### 🔴 第 1 条（最伤）：主流程没有「分段降级」，一次抛错 = 整件作品报废

**状态**：评审中期这条是「永久黑屏」（前两版实测 #3、#6 定格在遮罩 15 秒、零提示）；**评审末期作者补了全局兜底，黑屏变成了有字的错误页**。所以这里不再是「零反馈」问题，而是「一个零件坏了，整台机器陪葬」的问题。

**证据**：
- 0-A 的 `_col`：一次漏声明 → **点星读诗全废**，而且因为异常没冒到 window，连兜底都兜不到。
- 故障 #3（`DUFU.cats` 改名）：一行 schema 漂移 → **整页不可用**，用户只得到一句「初始化时出错：Uncaught TypeError…」。
- 故障 #2、#4（`ANALYSIS`/`COLLATION` 语法错）：**整块内容静默消失**，兜底完全不知道。

**为什么仍然最伤**：这三条是同一个病根——**代码把「初始化成功」当成一个全有或全无的原子事件**。只要有一个字段、一个模块不对劲，就整件作品归零或整块内容归零；而这部作品恰恰是「数据驱动 + 可选模块」的结构，字段最容易漂。

**改法：三件事，每件都不大**

1. **给启动链加分段保护**（现在还没有）：坏一块，退一块，别一起死。
2. **加数据形状校验**（现在还没有）：把「DUFU 在不在」升级成「poems/cats/meta 齐不齐、每首诗有没有 t 和 L」。
3. **把同步调用栈也纳入观测**：`select()` 这类事件处理里的抛错不会冒到 window，要么在 `select` 外层包一层 try/catch，要么在 click 的入口统一兜。

第 1 件事的写法如下。其中「全局 error 兜底 + 8 秒 watchdog」这一段 10:40 版已经实现，可以对照着看**还差哪几段**：

```js
// 1) 在 IIFE 最开头就装兜底——必须在任何可能抛错的调用之前
var __booted = false, __fatalShown = false;
function showFatal(msg){
  if (__fatalShown) return;
  __fatalShown = true;
  var el = document.getElementById('load');
  if (!el) return;
  el.classList.remove('up');
  el.innerHTML = '<div style="max-width:34em;text-align:center;font:15px/2 serif;color:#ece7db">'
    + '<div style="letter-spacing:.3em;color:#c9a227;margin-bottom:1.2em">星 海 暂 时 没 有 亮 起</div>'
    + '<div style="color:#8a8578">' + msg + '</div>'
    + '<div style="margin-top:1.6em;color:#5d5a52;font-size:12px">可以尝试：换 Chrome/Edge 打开、刷新一次、把文件放到纯英文路径下。</div></div>';
}
window.addEventListener('error', function(e){ showFatal('初始化时出错：' + (e.message||'未知错误')); });
window.addEventListener('unhandledrejection', function(e){ showFatal('初始化时出错：' + e.reason); });

// 2) 兜底要在启动之前就排好，而不是之后
setTimeout(function(){ if (!__booted) showFatal('加载超时（8 秒）。'); }, 8000);

// 3) 分段保护：坏一块就退一块，不要一起死
function step(name, fn){ try { fn(); } catch(e){ console.warn('[boot]', name, e); } }
step('grain', makeGrain);  step('wc', buildWC);   step('sky', buildSky);
step('mw', buildMW);       step('tex', buildNebulaTex);
step('layout', layoutGalaxyPoems); step('model', buildPoemModel);
step('cone', buildCone);   step('bloom', buildBloom);

// 4) 关键产物缺了就明确报错，而不是"段保护"把它变成静默缺一块
var missing = [];
if (!SKYTEX)     missing.push('天幕贴图');
if (!PC)         missing.push('白噪音星');
if (!pts.length) missing.push('诗句星点');
if (missing.length) showFatal('这几块没有初始化成功：' + missing.join('、') + '。');

// 5) 真的画出来了，才算"进去了"
requestAnimationFrame(function(){
  requestAnimationFrame(function(){ __booted = true; bootReady(); });
});
```

同时把 `bootReady` 改成「**首帧真正提交后再撤遮罩**」（治 §3.6 的 1.8 s 尾延迟）：

```js
function bootReady(){
  requestAnimationFrame(function(){          // 不用固定 900ms，改用“首帧已完成”信号
    document.getElementById('load').classList.add('up');
    setTimeout(function(){ var l=document.getElementById('load'); if(l&&l.parentNode) l.parentNode.removeChild(l); }, 700);
  });
}
```

**顺带**：把行 667 的守卫从“存在性检查”升级成“形状检查”：

```js
function validate(D){
  if (!D || !Array.isArray(D.poems) || !D.poems.length) return '诗数据为空';
  if (!Array.isArray(D.cats))  return '分类数据缺失（cats）';
  if (!D.meta)                  return '生平数据缺失（meta）';
  for (var i=0;i<D.poems.length;i++){
    var p = D.poems[i];
    if (typeof p.t!=='string' || !Array.isArray(p.L)) return '第 '+i+' 首诗字段不全';
  }
  return null;
}
```

### 🔴 第 2 条：单文件 79% 是内联图片，且主推件旁边缺 `art/`

**证据**：§3.4 体积表（4,743,442 B / 79.0%）；§3.5 交付目录结构（`交付/` 下无 `art/`），1437 首诗配图 404；112 KB 孤儿图；精选诗双层加载。
**为什么最伤**：它同时打中“体积”“离线”“交付完整性”三个卖点。评委如果按 `使用说明.txt` 的描述去找“断网双击即开 + 1468 幅配图”，会在单文件版里看到 1437 张空白——而且是**静默空白**。

**改法（按性价比排序）**：

1. **删掉孤儿键**（1 行，立省 112 KB）：构建脚本里加

   ```js
   // 04_bundle.py 出图前：只保留 DUFU.art 里真实存在的 slug
   const used = new Set(Object.values(DUFU.art));
   for (const k of Object.keys(ART_DATA)) if (!used.has(k)) delete ART_DATA[k];
   ```

2. **精选图从 base64 换成“内联 520 px 缩略图 + 全图外置”**：31 张里每张 115 KB 是**全分辨率** JPEG。卡面宽度不超过 520 px，内联 520 px 宽的 WebP（质量 72）通常 25–35 KB，31 张 ≈ 0.9 MB。单文件从 6.0 MB 降到 **≈ 2.2 MB**，卡片观感几乎无损（背后还有 `art/opt/` 全图可兜底）。
3. **单文件版不要和 `art/` 抢戏**：要么把 `art/opt/*.jpg` 一起放进 `交付/`（31 张，约 6 MB，目录名就叫 `art/`），要么在卡面显式写一句“精选 30 幅已内联；其余 1438 幅见《全图版》”。**沉默地 404 是最差选项。**
4. **精选诗别双层加载**：`layers` 里既然已经有内联图，就不要再拼 `url(art/all/...)`；只有当 `curated` 为空时才回落到 bulk。

### 🔴 第 3 条：星空只能用鼠标选中 —— 键盘与低视力用户完全进不去

**证据**：

- 全项目 `<button>` = **0** 个；`tabindex` 只有 **3** 处（声音开关、上一页/下一页），`role` 只有 3 处。
- `<canvas id="sky">` 无 `tabindex`、无 `role`、无 `aria-label`；方向键只改 `cam.yaw/pitch`（行 2421–2430），**没有任何键能把“焦点”从一颗星移到另一颗、也没有键能打开诗卡**。
- 8 种小字颜色对比度低于 4.5:1：`#3f3d37` **1.88**、`#4a4740` **2.20**、`#4e4b44` **2.34**、`#55524a` **2.61**、`#5d5a52` **2.96**、`#6a675e` **3.60**、`#6f6b61` **3.83**、`#7e7a6e` 4.75（勉强）。而它们大量用于 `--t1:9px / --t2:11px` 的编号与图例。
- `prefers-reduced-motion` = **0** 处；全屏星点闪烁 + 颗粒层 `animation: grainShift .9s steps(3) infinite` 不停。
- `cursor:none` 出现 **23** 次，全局生效。

**改法**：

```js
// A. 让星空可聚焦、可遍历（约 40 行，性价比最高）
cv.setAttribute('tabindex','0');
cv.setAttribute('role','application');
cv.setAttribute('aria-label','杜诗星海：1468 首诗的天空。方向键移动选中，回车打开。');
var kbFocus = null;
cv.addEventListener('keydown', function(e){
  if (e.key==='Enter' && kbFocus){ select(kbFocus); e.preventDefault(); return; }
  if (e.key==='Escape'){ closeCard(); return; }
  var dirs = {ArrowRight:[1,0], ArrowLeft:[-1,0], ArrowUp:[0,1], ArrowDown:[0,-1]};
  var d = dirs[e.key]; if (!d) return;
  e.preventDefault();
  var from = kbFocus && kbFocus._q ? kbFocus._q : {sx:CX, sy:CY};
  var best = null, bestScore = 1e9;
  for (var i=0;i<pts.length;i++){
    var q = pts[i]._q; if (!q) continue;
    var dx = q.sx-from.sx, dy = q.sy-from.sy;
    var along = dx*d[0] + dy*d[1];
    if (along <= 4) continue;                       // 必须在该方向
    var across = Math.abs(dx*d[1] - dy*d[0]);
    var score = along + across*2;
    if (score < bestScore){ bestScore = score; best = pts[i]; }
  }
  if (best){ kbFocus = best; hover = best; render(performance.now()); }
});
```

同时：

- `setPeriod/tour` 里那套“高亮”已经存在，键盘选中时直接复用 `hover` 渲染即可，**不必新写视觉**。
- 对比度：把 `#3f3d37/#4a4740/#4e4b44/#5d5a52/#6a675e` 统一抬到 **≥ `#8a8578`（5.53:1）**；9 px 的字建议一并提到 10–11 px。
- 加 `@media (prefers-reduced-motion: reduce){ #grain{animation:none} }`，并把 `autoSpin` 默认置 false。
- `cursor:none` 保留（有自定义光标 `#cur`），但要加 `@media (hover:none){ body{cursor:auto} }`，触屏设备上没人需要隐形光标。

## 7. 其余问题（按严重度排列，均实测/查证）

**7.1 天幕的三种说法，互相对不上**（这条比看起来严重）

| 出处 | 说的是 |
|---|---|
| `使用说明.txt` | “天幕照片：ESO / S. Brunier 全天银河全景（eso0932a），CC BY 4.0，已重投影并调色” |
| `docs/技术方法说明.md` §六 | “背景不是照片，也不是程序化贴图，而是**九万首机器写的诗**” |
| 代码 | 512×256 三维值噪声 + 两段域扭曲 → 上采样 2048×1024（`buildNebulaTex`，行 1134）+ 9,000 粒噪声星（`buildCone`，行 1081） |

三份必须收敛成一份。答辩时被问“天幕到底怎么来的”，三个答案会互相拆台。顺带：`sky.jpg` 若真不用，那段 CC BY 署名也要一起撤——**为一张没用的图署名**，和**用了图没署名**一样是硬伤。

**7.2 `probe.src = curated || bulk`（行 2353）的兜底永远不会触发**：`curated` 是 data URI 时必然成功，`onerror` 不会来。想探测 bulk，必须直接 `probe.src = bulk`。

**7.3 `buildSky()` 被连调两次**（行 3341），第二次结果立刻被 `SKY=null` 丢弃。0.4–5 ms 的纯浪费，也说明这行是拼接式改出来的。

**7.4 `__DUFU_DEBUG` 进了发布包**（行 3376），暴露 `select / state / redraw / cam / pts`。调试方便，但发布构建应剥离。

**7.5 配图靠下标推算**：`('0000'+p.i).slice(-4)`。一旦 `p.i` 超过 9999 或数据重排，图与诗会**静默错位**（不报错，只是配错图）。建议在 `DUFU` 里存 slug 而不是靠下标。

**7.6 44 个外链出处**在离线环境下点击会失败。若渲染成可点链接，建议加 `target="_blank" rel="noopener"`，并在离线时给 `title` 提示“需联网”。

**7.7 数字对不上**：`使用说明.txt` 说“精选 30 幅”，代码里 `ART_DATA` 是 31 个键（其中 1 个孤儿）。统一一下，免得被追问。

## 9. 总评

**做得好的地方，值得在答辩里主动讲**：

- 1,468 颗诗星 + 9,000 粒噪声 + 2,048×1,024 程序化天幕，在 1440×900 上稳定 11–13 ms/帧，**且与 DPR 无关**——这是真正吃透了 Canvas 2D 的表现。
- 全程 2 个网络请求（其中 1 个还是我这边路径不对导致的 404），**离线零依赖**名副其实。
- 连开 40 张诗卡后 JS 堆不涨——**没有泄漏**，这在手写渲染器里很少见。
- 2,636 行没有任何框架，命名与注释统一，`esc()` 一路贯彻，可读性优于大部分同类作品。

**必须修的地方，按顺序**：启动错误边界 → 单文件体积与素材目录 → 键盘可达性。前两条各约半天工作量，第三条约一天；做完这三条，分数可以从 72 提到 **85 上下**，而且**不需要动任何一行渲染代码**。

> 一句实话：这件作品的“贵”在审美和手写渲染上，它的“脆”在工程习惯上。而交付物是要在别人的电脑上、别人不知道发生了什么的情况下，被双击打开的。
